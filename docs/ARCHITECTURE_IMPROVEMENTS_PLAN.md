# План точечных улучшений архитектуры TroughGame

Дата: 2026-10-09. Исходная ревизия: `bf7717e`.

Это новый план после решения отказаться от обязательных слоёв Clean Architecture
внутри фич. Предыдущий `FEATURE_LAYERS_PLAN.md` сохраняется как материал анализа,
но его схема слоёв не является направлением дальнейшей миграции.
На момент составления плана была изменена только документация. Предложения ниже
фиксируют исходный объём до независимого аудита и согласования приоритетов.

## Результат согласованного этапа — 2026-10-10

После аудита реализован согласованный список из семи исправлений:

1. Исправлены пути `PlayerPrefabTests` и противоречия действующих документов.
2. Исправлена финализация `SceneFlow`: переход остаётся заблокированным до окончания
   cleanup, ошибки скрытия отдельных presenters не прерывают остальную очистку.
3. Добавлена проверка Player prefab до создания сетевого объекта.
4. Добавлены ранние проверки Player spawn points и критичных параметров Dodge/Dash;
   правила и ошибки размещены в отдельных статических `*Validation` и `*Errors`.
5. Валидатор разрешает базовые типы с учётом namespace, imports, aliases и generic
   arity; добавлены положительные и отрицательные регрессионные проверки.
6. `EnemySteeringService` возвращает направление и точку подхода в `EnemySteeringData`;
   chasing использует один результат, debug-визуализация читает `LastCalculation`.
7. `DebugConsoleFeature` получает и сохраняет `IClassFactory` при инициализации.

Дополнительно исправлены ошибочное ожидание движения к центру игрока в PlayMode-тесте
врагов и чтение `TargetEntityId` после `ClearTargetEntityId()`: сохранённый sentinel
`none:-1` теперь распознаётся как `NetworkEntityIdData.None`.

Вычисления steering сохранены в сервисе; отдельный processor не вводился.
Остальные исходные предложения оцениваются по результатам аудита и не являются
автоматически принятыми задачами.

## Вывод анализа

Основа `Contexts → Features → Scripts` подходит проекту. Главная возможность
улучшения — уточнить ответственность объектов, владение состоянием и ресурсами,
поведение при ошибках и границы между фичами. Перекладывание классов по слоям
само по себе эти вопросы не решает.

Уже удачные решения: единый запуск через initialization flow; отдельные контракты
симуляции и столкновений; processors для правил движения; разделение LocalSave на
сервис, хранилища и сериализаторы; отдельные реестры и фабрики сетевых сущностей.
Их стоит развивать, а не заменять новой архитектурной системой.

План содержит **7 точечных и 7 общих улучшений**. Общие изменения внедряются
через конкретные затронутые фичи, а не массовым переписыванием проекта.

### Достоверность и приоритеты

- **Сценарий по коду:** видна конкретная ветка, ведущая к неконсистентному состоянию.
  Это основание для исправления, но не утверждение о воспроизведённом runtime-баге.
- **Структура:** ответственность смешана или правило применяется неодинаково;
  исправление должно принести понятную пользу при сопровождении.
- **Гипотеза:** сначала нужны измерение или интеграционный тест. Реорганизация
  ради предположения не включается в обязательную работу.
- **P1:** согласованность состояния и завершение операций при сбоях.
- **P2:** читаемость, проверяемость и предотвращение повторяющихся проблем.
- **P3:** условный следующий шаг, когда появится подтверждённая потребность.

## Точечные улучшения

### L1. Выделить вычисления из EnemySteeringService — P2, структура

**Основание:** [EnemySteeringService](D:/Repositories/TroughGame/Assets/ProjectCore/Contexts/TechnicalPrototype/Features/Enemy/Scripts/Managers/Services/EnemySteeringService.cs:23)
одновременно получает root через `INetworkBehaviourAccessor`, читает `Transform`,
обходимый список из registry, рассчитывает положение в группе, separation и направление.
`ApproachPosition` хранится как побочный результат последнего `CalculateDirection`.

**Решение:** сервис собирает входные данные текущего тика; небольшой
`EnemySteeringProcessor` в `Other/Processors` выполняет расчёт и возвращает
`EnemySteeringData` с направлением и approach position в одном результате.
Processor получает позиции, сведения о целях/порядке соседей и параметры,
а не root, registry или сетевой accessor. Unity `Vector2`/`Mathf` допустимы;
в `Shared` этот алгоритм переносить не требуется.

**Обоснование:** отделяется правило поведения от способа чтения мира и исчезает
скрытая зависимость от порядка чтения свойства после вызова метода.
Извлечение сохраняет алгоритм, а не одновременно меняет поведение AI.

**Ожидаемый результат:** формулу движения можно понять и проверить на фиксированных
данных без создания Fusion-сущностей. Изменение состава сетевого root не затрагивает
математику steering. Само извлечение не обещает ускорения.

**Проверка пользы:** сценарии одиночного врага, общей цели, совпадающих позиций,
separation и смены цели дают прежние результаты с численным допуском;
chasing использует один возвращённый результат. После прогрева новые входные
данные не создают дополнительных коллекций каждый тик.

**Цена и риски:** несколько небольших типов и сбор входа. Сохранить порядок группы,
точность и правила fallback. Не копировать каждый список соседей на каждого врага;
ownership/reentrancy временных буферов определить вместе с L3.

### L2. Выделить правила retarget и решения о dash — P2, структура

**Основание:** [EnemyBehaviourChasingState](D:/Repositories/TroughGame/Assets/ProjectCore/Contexts/TechnicalPrototype/Features/Enemy/Scripts/Views/States/EnemyBehaviourChasingState.cs:133)
координирует поиск цели, выдержку retarget delay, steering, способности и остановку.
[EnemyDashChaseAbilityProcessor](D:/Repositories/TroughGame/Assets/ProjectCore/Contexts/TechnicalPrototype/Features/Enemy/Scripts/Other/Processors/EnemyDashChaseAbilityProcessor.cs:34)
несмотря на имя processor читает сетевой accessor, `Transform`, cooldown и SO.

**Решение:** вынести retarget policy в processor с явными текущей целью,
кандидатом, расстояниями, elapsed time и tick delta; вернуть решение и новое
состояние выдержки. Хранение этого состояния оставить у существующего владельца.
Для dash передавать позицию, доступность cooldown, допустимость цели и необходимые
параметры. Chasing state сохраняет последовательность и применение решений.

**Обоснование:** правила выбора можно читать отдельно от orchestration текущего тика.
Нет необходимости строить универсальный ability framework или новую state machine.

**Ожидаемый результат:** настройка задержки и допуска dash локализована; крайние
условия проверяются без NetworkRunner. Состояние не дублируется в сервисе и root.

**Проверка пользы:** равные расстояния; смена кандидата сбрасывает выдержку;
цель исчезает; delay=0; cooldown не готов; distance на границе допуска;
существующий dash прерывает обычный chase input. Сохранить Player-only eligibility
и порядок «первая подходящая способность побеждает».

**Цена и риски:** явные данные могут раздуть сигнатуру — использовать связный
input struct только там, где это делает вызов понятнее. State machine сейчас
работает только на State Authority; rollback-проблема полей retarget не доказана.
Не менять их сетевую репликацию в этом рефакторинге.

### L3. Уточнить семантику и стоимость entity queries — P2, структура + гипотеза о масштабе

**Основание:** [GameEntityComponentAccessorService](D:/Repositories/TroughGame/Assets/ProjectCore/Contexts/GameCore/Features/NetworkEntities/Scripts/Managers/Services/GameEntityComponentAccessorService.cs:34)
создаёт временные списки даже для первого найденного ID. Метод
`TryFindFirstEntityIdSortedBy` уже выбирает минимум линейно, **не сортирует**,
но собирает ID и повторно получает компоненты. Steering многократно обходит врагов.

**Решение:** предоставить операции поиска первого и минимального элемента за
один проход без полного материализованного списка. Уточнить имя операции
минимума, сохранив совместимость при миграции. Для fill/sorted операций сохранить
выбор вызывающего кода. Прямой обход и обход snapshot должны иметь разные,
задокументированные гарантии изменения registry во время callback.

**Обоснование:** API выражает потребность, а не заставляет caller собирать все результаты.
Повторное создание коллекций на горячем пути устраняется там, где оно действительно есть.

**Ожидаемый результат:** меньше временных выделений на запросах AI и понятный выбор
между «любой», «ближайший» и «все». Ускорение игры и масштабный spatial index
пока остаются гипотезами, требующими профилирования.

**Проверка пользы:** сравнить GC Alloc и время query на одинаковых сценах с 10/50/100
врагами после прогрева; проверить tie-breaking и порядок. Тест с despawn внутри
`ApplyToAll` должен сохранять текущую допустимую семантику: там snapshot нужен.

**Цена и риски:** direct enumeration может сломаться при мутации registry;
общий reusable buffer — при вложенном вызове. Не заменять все snapshots live-обходом.
Spatial partitioning планировать отдельно только при измеренном узком месте.

### L4. Сделать переходы ScreenNavigation устойчивыми к сбою — P1, сценарий по коду

**Основание:** [TransitToScreenAsync](D:/Repositories/TroughGame/Assets/ProjectCore/Contexts/Template/Features/ScreenNavigation/Scripts/Managers/Systems/ScreenNavigationSystem.cs:229)
добавляет следующий view в root до `ShowAsync`, а в history — после всех await.
При отмене показа catch не удаляет этот view. Закрытие старой history по одному
может завершиться частично. В `GoBackAsync` тоже нет восстановления после
частично выполненного Show/Hide/Close.

**Решение:** явно разделить подготовку нового экрана, переключение активного
экрана и фиксацию history. Операция владеет незавершённым view и очищает его
при сбое. Добавить безопасную немедленную очистку и заранее определить политику
для необратимого `OnCloseAsync`: восстановление допустимого экрана либо
согласованное аварийное состояние history, а не обещание полного rollback.

**Обоснование:** визуальная и навигационная структуры должны описывать одни и те
же принадлежащие системе экраны после успеха, ошибки и отмены.

**Ожидаемый результат:** повторная навигация после отмены не оставляет неучтённых
view; история не указывает на уже удалённые экраны; cleanup не скрывает исходную ошибку.

**Проверка пользы:** отмена/исключение на Initialize, Show, Hide и Close; отмена
возврата назад; повторный переход после каждого сбоя. Проверять hierarchy,
history, активный экран и `IsTransitioning`, а не только возвращённый Result.

**Цена и риски:** наиболее чувствительное изменение UI-плана. Сначала определить
инварианты и написать проверки ошибочных веток. Не объединять ScreenNavigation
с Popup/LoadingScreen ради похожих методов.

### L5. Исправить финализацию SceneFlow — P1, сценарий по коду

**Основание:** [SceneFlowService](D:/Repositories/TroughGame/Assets/ProjectCore/Contexts/Template/Features/SceneFlow/Scripts/Managers/Services/SceneFlowService.cs:155)
сбрасывает `IsTransitioning` до await скрытия presenters. Ошибка одного Hide
прерывает закрытие остальных и может заменить исходный результат/исключение.
Cancellation catch отличается от общего catch очисткой состояния сцены.

**Решение:** сохранять блокировку до завершения финализации; закрывать все
затронутые presenters с отдельной обработкой ошибок; сохранять первичную причину
сбоя и диагностировать вторичные. Определить состояние readiness при отмене
инициализации и судьбу уже начавшейся Unity-загрузки. Для разных фаз перехода
применять явно выбранную cleanup policy, а не безусловно очищать текущую сцену.

**Обоснование:** завершение операции включает уборку перехода. Отмена до выхода
из старой сцены и отмена после загрузки новой требуют разных решений.

**Ожидаемый результат:** переходы не перекрываются во время Hide; один неисправный
presenter не оставляет остальные открытыми; callers видят реальную причину сбоя.

**Проверка пользы:** два presenters, один бросает на Hide; частичный Show;
отмена до Exit, во время загрузки и Initialize; повторный запрос во время cleanup.
Проверить readiness/lifetime и позднее завершение загрузки в Play Mode.

**Цена и риски:** закрытую/выгруженную Unity-сцену нельзя автоматически восстановить
присваиванием полей. Не объявлять переход «транзакцией с полным откатом».
SceneLoadingScreenBridge сохраняет свою небольшую интеграционную роль.

### L6. Отделить performance sampling от DebugConsoleController — P2, структура

**Основание:** [RenderPerformance](D:/Repositories/TroughGame/Assets/ProjectCore/Contexts/Template/Features/DebugConsole/Scripts/Managers/Controllers/DebugConsoleController.cs:450)
напрямую читает `Time` и Unity `Profiler`, одновременно обслуживая вкладки,
историю команд, selection и UI.

**Решение:** выделить небольшой provider performance data с Unity-реализацией,
возвращающий существующий `DebugConsolePerformanceData`. Controller сохраняет
расписание обновления и отображение. Visualization HUD adapter оставить
отдельной интеграцией; дополнительно дробить controller только при связной обязанности.

**Обоснование:** сбор runtime-показателей меняется независимо от поведения UI.

**Ожидаемый результат:** controller можно проверить на заданных показателях;
добавление метрики не требует изменения управления вкладками и команды.

**Проверка пользы:** deterministic fake-provider проверяет отображение/частоту;
скрытая вкладка не запрашивает ненужные показатели. Сравнить стоимость обновления.

**Цена и риски:** одна зависимость и реализация. Не делать интерфейс на каждую
функцию Profiler; у provider один связный результат и один владелец.

### L7. Сделать fallback источника времени наблюдаемым — P3, структура

**Основание:** [NtpTimeProvider](D:/Repositories/TroughGame/Assets/ProjectCore/Contexts/Template/Features/AppTime/Scripts/Managers/Providers/NtpTimeProvider.cs:25)
при любой не-cancellation ошибке молча переходит на локальный UTC.
Синхронная рабочая функция DNS/socket не получает cancellation token.

**Решение:** сохранить fallback, но показывать диагностике источник времени и
причину отказа. Если время сети является требованием startup, отдельно проверить
реальную отмену начатого запроса и ограничение всей операции, включая DNS.
Менять сетевую реализацию только после этого сценария, не ради абстрактных слоёв.

**Обоснование:** разработчик должен отличать корректный offline fallback от
неработающего источника, когда анализирует временные ошибки.

**Ожидаемый результат:** понятная диагностика без запрета offline-запуска.

**Проверка пользы:** недоступный сервер, некорректный ответ, отмена и корректный UTC;
fallback фиксируется единожды и не засоряет лог каждым вызовом `GetCurrentTime`.

**Цена и риски:** избегать бесконечных retries и блокировки запуска. При отсутствии
продуктовой зависимости от сетевого времени ограничиться диагностикой.

## Общие улучшения повторяющихся проблем

### G1. Единые гарантии сетевого спавна — P1, структура + сценарий по коду

**Основание:** [PlayerNetworkEntityFactory](D:/Repositories/TroughGame/Assets/ProjectCore/Contexts/TechnicalPrototype/Features/Player/Scripts/Managers/Factories/PlayerNetworkEntityFactory.cs:32)
проверяет тип root после `runner.Spawn`; если prefab неверный и spawn проходит,
метод бросает исключение без собственного despawn. [EnemyNetworkEntityFactory](D:/Repositories/TroughGame/Assets/ProjectCore/Contexts/TechnicalPrototype/Features/Enemy/Scripts/Managers/Factories/EnemyNetworkEntityFactory.cs:25)
проверяет prefab, тип root и authority заранее. Player/Enemy Despawn тоже
имеют неодинаковые проверки.

**Решение:** согласовать последовательность preflight → ID assignment до Spawned →
spawn → получение ожидаемого root и определённое поведение при частичном сбое.
Первым исправить Player. После проверки обеих фабрик выделить только совпадающий
механизм в NetworkEntities, используя/расширяя существующий BaseNetworkEntityFactory,
а не создавая параллельную систему фабрик. Authority/payload policy остаётся у фичи.

**Обоснование:** новая фича должна наследовать безопасные гарантии, а не копировать
одну из двух расходящихся реализаций.

**Ожидаемый результат:** неверный prefab отвергается до побочных эффектов;
успешно созданная сущность имеет ID; неуспех не оставляет бесхозный объект;
правила authority сохраняют различия Player и Enemy.

**Проверка пользы:** неверный root/prefab, остановленный runner, корректный игрок,
серверный враг, повторный despawn, попытка despawn чужого типа. Play Mode —
отсутствие лишней сущности в runner/registry после ошибки. Не требовать IDs без пропусков.

**Цена и риски:** Fusion callbacks, spawn modes и prefab loading; SDK-сбой не всегда
предоставляет объект для cleanup. Не копировать Enemy `IsServer`-ограничение в Player
без проверки поддерживаемых режимов. Shared не владеет Fusion-механизмом.

### G2. Валидировать авторские данные до использования — P2, структура

**Основание:** [PlayerSpawnComponent](D:/Repositories/TroughGame/Assets/ProjectCore/Contexts/TechnicalPrototype/Features/Player/Scripts/Views/Components/PlayerSpawnComponent.cs:59)
обнаруживает пустой/null spawn point только при подключении игрока. Enemy уже
имеет spawn validation. EnemyChaseConfig и DashMovementConfig используют `[Min]`,
но это не заменяет runtime-проверку значений и согласованности параметров.

**Решение:** фича проверяет необходимые serialized references, prefab и параметры
на этапе своей явной инициализации/readiness. Feature-specific `*Validation`
содержит связные проверки; OnValidate помогает автору, но не заменяет их.
Проверять положительную duration, конечность чисел и допустимые диапазоны.
Снимки config data вводить только для L1/L2 либо реальной потребности.

**Обоснование:** ошибку настройки лучше обнаружить до запуска gameplay,
с сообщением о конкретной фиче и ресурсе.

**Ожидаемый результат:** одинаковая точка отказа и понятная причина;
меньше случайных ошибок посреди network tick/подключения игрока.

**Проверка пользы:** пустые references, null внутри arrays, нулевая duration,
неконечные числа, корректные крайние значения. Initialization не объявляет
фичу готовой при ошибке. Не повторять уже имеющиеся проверки без необходимости.

**Цена и риски:** список проверок должен отражать реально используемые настройки.
Если SO преобразуется в snapshot, явно выбрать live-tuning или frozen-at-init
поведение; молчаливое изменение настройки дизайнером не должно теряться.

### G3. Уточнить публичные межфичевые контракты — P2, структура

**Основание:** EnemySteeringService, EnemyTargetingService и spawn/debug components
напрямую принимают `NetworkEntityRegistry`/`NetworkEntitySpawner`. При этом
`IGameEntityComponentAccessor`, `ICameraTargetRegistry` и movement contracts уже
показывают более узкие границы. Общие namespaces не выражают ownership фичи.

**Решение:** для чтения сначала использовать/дополнить существующий accessor,
если его ответственность подходит. Недостающий связный query contract выделять
в NetworkEntities; mutation и spawn не выдавать читателю вместе с запросами.
Spawn-клиентам предоставить нужный контракт, если он снижает зависимость от
механизма. В каждой затронутой фиче назвать публичные входы и внутренние реализации.

**Обоснование:** контракт ограничивает возможности потребителя и стоимость
изменения поставщика. Это полезнее одинаковых папок Domain/Application.

**Ожидаемый результат:** Enemy зависит от доступных операций поиска/чтения,
а не устройства registry; такие зависимости заменяются в тестах.
Composition root по-прежнему знает конкретные реализации.

**Проверка пользы:** сохранить DI bindings и существующие targeting/prefab тесты;
новый consumer работает с fake-контрактом. Контракт не является копией всех
публичных методов класса и не вводит цепь бессмысленных forwarding adapters.

**Цена и риски:** лишние интерфейсы способны ухудшить читаемость.
Unity/Fusion-типы разрешены в контракте, если SDK-семантика нужна потребителю.
Ссылка на публичный идентификатор Player сама по себе не доказывает нарушение;
Player-only dash policy должна оставаться явной, а не незаметно расширяться.

### G4. Общие гарантии async-операций и cleanup — P2, повторяющийся паттерн

**Основание:** L4/L5 показывают расходящиеся ошибочные ветки; Popup/LoadingScreen
уже имеют cleanup и lifetime, DebugConsole отменяет операции при Detach.
В SceneFlow token запроса также становится родителем lifetime новой сцены.

**Решение:** для публичной async-операции определить владельца, request cancellation,
lifetime результата и обязательную финализацию. Для SceneFlow отдельно решить,
должен ли отменённый после успешного Load caller завершать жизнь сцены.
Root `.Forget()` допустим с определённым наблюдением ошибок и владельцем.
Обязательная очистка не использует уже отменённый request token; при этом она
имеет гарантированный путь завершения, без бесконечного await.

**Обоснование:** отмена ожидания, отмена работы и уничтожение её результата —
разные события. Их связь должна быть решением capability, а не случайным эффектом CTS.

**Ожидаемый результат:** одинаково понятное поведение при scene unload,
detach view, cancel request и cleanup failure; первичная ошибка сохраняется.
Нужна общая политика, а не общий менеджер всех UniTask.

**Проверка пользы:** у L4/L5 тестировать каждую границу await; у Console — старую
команду, заканчивающуюся после Detach/нового Attach; у Popup/Loading — отсутствие
лишних view/tasks после Dispose. Поздний результат не меняет состояние нового owner.

**Цена и риски:** поведение существующих callers может измениться при разделении
tokens. Сначала описать контракт и проверить вызовы Preloader/SceneFlow.
Не считать каждый `.Forget` ошибкой: внутренний system уже может наблюдать исключения.

### G5. Явные правила entity lifecycle, authority и времени — P2, структура + гипотезы

**Основание:** [BaseNetworkEntityRoot](D:/Repositories/TroughGame/Assets/ProjectCore/Contexts/GameCore/Features/NetworkEntities/Scripts/Abstract/BaseNetworkEntityRoot.cs:61)
регистрирует сущность до создания/инициализации components; optional registry
или invalid ID приводят к пропуску регистрации. `INetworkEntityComponent`
имеет Init/Tick/Render, но не общий teardown. При этом CameraTargetComponent
уже правильно unregister-ится через Fusion `Despawned`.

**Решение:** описать инварианты готовности root, допустимый порядок components,
владельца регистрации и поведение при частичном Init failure. Проверить повторный
spawn/despawn; при необходимости добавить узкий teardown только компонентам,
которые реально держат ресурсы. Не делать вторую централизованную систему
поверх уже работающего Fusion lifecycle. Optional registry в runtime должна
иметь явно обоснованный сценарий, отдельный от удобства isolated tests.

Параллельно закрепить: networked state — единственный источник истины;
решения симуляции используют tick delta/TickTimer и допустимый authority;
Render отвечает за эффекты; debug UI использует unscaled time; AppTime — UTC.

**Обоснование:** локальный рефакторинг не должен создавать рассинхрон состояния
или второе владение ресурсом. Правило опирается на границы Unity/Fusion.

**Ожидаемый результат:** понятная готовность сущности, симметричный lifecycle там,
где он необходим; одинаковое понимание prediction/tick/render при добавлении фич.

**Проверка пользы:** partial Init failure, повторный spawn/despawn, registry/camera
после удаления, authority player/enemy. Rollback и reuse/pooling проверять только
в реально используемом режиме. Утечка/pooling-баг по текущему коду не доказаны.

**Цена и риски:** самый чувствительный общий пункт для сетевой симуляции.
Не переставлять регистрацию после Init без проверки зависимостей Init;
не менять Networked layout и не вводить универсальный IClock на этом этапе.

### G6. Сузить runtime-ответственность Feature-компонентов — P2, структура

**Основание:** [DebugConsoleFeature](D:/Repositories/TroughGame/Assets/ProjectCore/Contexts/Template/Features/DebugConsole/Scripts/Init/DebugConsoleFeature.cs:56)
создаёт/уничтожает console при переключениях, использует Resolve в runtime
callback и владеет подпиской. [DebugVisualizationFeature](D:/Repositories/TroughGame/Assets/ProjectCore/Contexts/Template/Features/DebugVisualization/Scripts/Init/DebugVisualizationFeature.cs:53)
обрабатывает enable/shutdown и static attach/detach. Текущие OnDestroy уже отписываются.

**Решение:** небольшой coordinator каждой capability получает зависимости
через DI и владеет переключением, подписками и runtime-объектом/backend.
Feature сохраняет serialized references, bindings и вызов явной initialization.
Настройки передаются coordinator без runtime service location.
У cleanup один владелец и безопасный повторный вызов.

**Обоснование:** entry фичи описывает композицию и запуск, а runtime-поведение
можно сопровождать и проверять отдельно от GameObject.

**Ожидаемый результат:** toggles/подписки не спрятаны в bootstrap-коде;
создание console проверяется через существующий IClassFactory;
конкретный порядок DI disposal/OnDestroy не вызывает двойного уничтожения.

**Проверка пользы:** enable/disable несколько раз, Dispose в любом состоянии,
одна подписка, один живой console, Detached static facade после завершения.
Существующий FeatureLifecycleAdapter не переписывать: helpers уже централизованы.

**Цена и риски:** один coordinator оправдан полноценным runtime ownership;
для фич с одними bindings новый coordinator не нужен. DontDestroyOnLoad
и documented debug facade сохраняют текущую семантику.

### G7. Согласовать правила и усилить проверку границ — P2, структура

**Основание:** [ARCHITECTURE_RULES](D:/Repositories/TroughGame/docs/ARCHITECTURE_RULES.md:292)
упоминает default runtime assembly, хотя есть `ProjectCore.Runtime.asmdef`;
раздел Views расходится с CONVENTIONS в допуске VisualElement.
[Валидатор](D:/Repositories/TroughGame/Tools/Architecture/Validate-Architecture.ps1:697)
индексирует primary types по короткому имени: активный и legacy PlayerFeature,
PlayerNetworkEntityComponent и LocomotionMovementConfig имеют одинаковые имена.
Shared dependencies проверяются, но полноценного анализа направления ссылок
между контекстами/фичами существующая проверка не выполняет.

**Решение:** сначала согласовать документы с текущим кодом и решением без
обязательных CA layers. Уточнить, что Views — нынешняя категория Unity-facing
типов, а не доказательство роли Presentation. Учитывать полное имя типа при
анализе наследования и неоднозначность вместо молчаливого выбора первого типа.
Отдельно добавить отчёт о ссылках по context/feature ownership; начать с
диагностики и постепенно включать строгие правила для подтверждённых границ.
Для semantic checks предпочтителен доступный C# semantic tooling, не regex
по using: несколько фич разделяют namespace.

**Обоснование:** стандартизация полезна, когда правила согласованы и инструмент
ловит реальные нарушения, а не только неверный suffix.

**Ожидаемый результат:** зелёная проверка означает проверку заявленных границ;
тип из Prototype не влияет на классификацию активного типа; новые нарушения
context direction обнаруживаются до code review.

**Проверка пользы:** negative/positive fixtures для одноимённых типов разных
namespaces, запрещённой context dependency, разрешённой композиции, Unity
VisualElement и допустимого межфичевого public contract. Текущий repo проходит
после отдельно рассмотренных исправлений, не через широкое подавление предупреждений.

**Цена и риски:** semantic tooling может увеличить стоимость поддержки.
Не вводить новые asmdef и namespaces ради проверки; существующие сохраняются.
Жёсткие проверки feature internals включать после описания публичных контрактов,
иначе легитимные integrations станут ложными нарушениями.

3. Проверены заявленные ошибочные/граничные сценарии. Измерения производительности
   приводятся только там, где они были сделаны, а не выводятся из количества классов.
4. Структурный validator, relevant build, `git diff --check` проходят; Editor/Play
   проверки выбираются по изменённому поведению. `.meta` сохраняются при moves.
5. Если абстракция лишь добавила переадресацию и не дала заявленной пользы,

## Что сейчас не включать в миграцию

- Четыре обязательных слоя, новые asmdef или вложенные namespaces каждой фичи.
- Перенос feature-specific расчётов в Shared только из-за отсутствия MonoBehaviour.
- Универсальные wrappers для Vector2, UniTask, Physics2D, NetworkRunner и часов.
- Новую parallel-модель поверх Networked state или blanket-правило «любой processor stateless».
- Дробление CheatService, LocalSaveService, LevelCollisionService и DebugVisualizationRunner
  по числу строк; сначала требуется отдельная несвязная ответственность или проблема.
- Перенос Enemy/Player из TechnicalPrototype в GameCore без второго реального
  потребителя. Для повторного использования сначала отделяется scene-specific wiring.
- Реорганизацию legacy Prototype и удаление thin-фасадов Combat/Movement без
  проверки, какую полезную границу они обеспечивают.

Результат этого плана — несколько проверяемых правил ответственности и конкретных
исправлений, которые можно применять при развитии проекта без постоянных исключений.
