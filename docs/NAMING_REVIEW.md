# Анализ нейминга типов и суффиксов

Дата: 2026-10-11. Основа: текущий код после коммита `a8a2289`.

## Реализация первого этапа

После согласования предложений из таблицы первого этапа выполнено:

- `Editor`, `EditorWindow`, `AttributeDrawer` разрешены и описаны одинаково
  для контекстных и feature-owned инструментов.
- `EnemyBehaviourState`, `MemberHandler`, `PayloadMemberHandler` переименованы
  в `BaseEnemyBehaviourState`, `BaseMemberHandler`, `BasePayloadMemberHandler`.
  Для типов добавлены/обновлены `MovedFrom`, GUID сохранены.
- Префикс `Base` проверяется для top-level abstract классов во всех категориях
  контекстов. Четыре семейства generic definitions сохраняют имена;
  исключение ограничено владельцем, arity и соответствующей `Base*Definition`.
  Shared `HandlerPayload` остаётся в независимой области правил Shared.
- Булевы свойства из согласованного списка переименованы: `IsHUDVisible`,
  `IsEnabledInEditor` и остальные признаки доступности, `ShouldOpenOnStart`,
  `ShouldUseChannelValueColors`. Связанная настройка стала
  `ShouldShowHUDOnStart`. Сериализованные поля имеют `FormerlySerializedAs`.
- Документированы `Was` и исключения для operation-result методов и SDK API.
- Закреплены и применены формы `Id`, `UI`, `HUD`, `DTO`, `FPS`, `FOV`, `Json`,
  `Ntp`. Три `DebugVisualizationHud*` типа/файла теперь используют `HUD`.
  Unity `GetInstanceID` сохраняет оригинальное имя.

Проверки первого этапа: Strict — 533 скрипта, 167 ресурсов, 0 ошибок и
предупреждений; 21 новая регрессионная проверка нейминга, 12 проверок разрешения
типов и 17 проверок ресурсов прошли. Собственные Unity-тесты: 134 Editor и
6 Play прошли. Runtime build: 0 ошибок, 8 прежних предупреждений MSB3277.

Отдельно подтверждены сохранение 6 GUID и значений 44 конфигураций. Миграция
шести сериализованных полей проверена на временных нативных Unity-ассетах со
старыми именами и недефолтными значениями, включая вложенные настройки консоли.
Временные ассеты удалены. JSON-загрузка через EditorJsonUtility не использована
как доказательство поддержки FormerlySerializedAs.

Разбор System, дополнительных соглашений и оставшихся мест Validation/Errors

## Закрепление устоявшихся соглашений

После отдельного согласования следующий этап закреплён в
[`CONVENTIONS.md`](CONVENTIONS.md); архитектурные правила ссылаются на этот
словарь, а ограничения автоматической проверки уточнены в README валидатора.

- Имя интерфейса описывает доступную возможность; реализация — роль или
  механизм. Суффиксы не обязаны совпадать. Предметные/маркерные контракты
  (`IScene`, `ICameraTarget`, `IEnemyAbility`) не требуют искусственного суффикса.
- Описаны ответственность, границы и существующие примеры дополнительных
  ролей контрактов. `Accessor` предоставляет чтение; `Mutator` контролируемые
  изменения и может включать чтение. `Reader` допускает захват снимка данных.
- Закреплены смысловой порядок частей имени без обязательного повторения
  названия Feature, механизм перед предметом при необходимости, семантические
  generic-параметры и допустимость универсального `T`.
- Метод инъекции называется `Construct`; для различимого метода базы допустим
  `ConstructBase<Type>`. В `ClimbDetectorComponent` и `GroundDetectorComponent`
  `Constructor` переименован в `Construct`; атрибуты и зависимости сохранены.
- Различены `Empty`, `Default`, `NoOp`, объяснены составные имена
  `SettingsConfig`/`CatalogConfig` и область правил для вложенных типов.
- Смысловые решения проверяются при code review. Strict подтверждает только
  реализованные объективные проверки, а не полное соблюдение словаря ролей.

Проверки этого этапа: Strict — 533 скрипта, 167 ресурсов, 0 ошибок и
предупреждений; все 50 регрессионных проверок валидатора прошли. Собственные
Unity-тесты: 134 Editor и 6 Play прошли без пропусков. Unity recompile —
0 ошибок и предупреждений; Runtime build — 0 ошибок, 8 прежних MSB3277.
Проверки staged/unstaged diff прошли. Сериализованные ассеты не изменены.

Разбор `System`/`Service` и оставшихся мест Validation/Errors остаётся отдельным
этапом. Исходный порядок рекомендаций ниже сохранён как результат анализа;
устоявшиеся соглашения реализованы раньше разбора System по решению пользователя.

## Вывод

Физические категории и суффиксы проекта в основном согласованы. Основные
проблемы — неполнота общего словаря ролей, неоднозначные требования к базовым
типам и сокращениям, а также несколько имён, которые обещают другую
ответственность. Массовое переименование всех типов не оправдано.

Проверены имена и расположение 533 собственных C# файлов: 374 основных класса,
118 интерфейсов, 24 структуры и 17 перечислений. Это включает тесты, Shared
и legacy-контекст Prototype; импортированные Plugins/ThirdParty исключены.
Поведение типов проверялось адресно для спорных ролей, а не как полный аудит
реализации каждого метода.

Strict-валидатор: 533 скрипта, 167 ресурсов, 0 ошибок и 0 предупреждений.
Этот результат подтверждает реализованные проверки, но не полное соблюдение
всех текстовых требований к именам и ответственности.

Изменений production-кода и действующих соглашений в рамках анализа нет.

## 1. Подтверждённые расхождения

### 1.1. Таблица Editor не соответствует коду и валидатору

`CONVENTIONS.md`, таблица Other, разрешает `Editor` и `EditorWindow`, в том
числе для drawers. Между тем существующий тип называется
`SubclassSelectorAttributeDrawer` и находится в
`Template/Scripts/Other/Editor`. Валидатор явно разрешает там только
`AttributeDrawer`; для feature-owned Editor он разрешает `Editor` и
`EditorWindow`.

Предложение: задокументировать `AttributeDrawer` для обработчика свойства
Unity и согласовать допустимые суффиксы в обеих ветках валидатора. Конкретный
класс переименовывать не нужно. Будущий контекстный `SomeEditorWindow` сейчас
получил бы ошибку суффикса, хотя общий стандарт его допускает.

Результат: тип инструмента определяется назначением, а не тем, лежит он в
Feature или непосредственно в контексте.

### 1.2. Часть булевых имён нарушает буквальное правило

В `CONVENTIONS.md` разрешены только префиксы `Is`, `Has`, `Can`, `Should`.
Примеры из кода:

| Существующее имя | Предложение | Причина |
| --- | --- | --- |
| `HudVisible` в DebugVisualization | `IsHUDVisible`, если выбран формат `HUD` | Состояние видимости. |
| `EnabledInEditor`, `EnabledInDevelopmentBuild`, `EnabledInReleaseBuild`, `EnabledOnDedicatedServer` в `DebugToolsSettingsConfig` | `IsEnabledInEditor` и аналогично | Признак разрешённости. |
| `UseChannelValueColors` в `DebugVisualizationHudAdapter` | `ShouldUseChannelValueColors` | Настройка поведения. |
| `OpenOnStart` в `DebugConsoleSettings` | `ShouldOpenOnStart` | Настройка поведения. |
| `WasPressed`, `WasReleased`, `WasPerformed` в `LocalButtonStateData` | Оставить и разрешить `Was` | Событие в уже захваченном input sample, а не текущее состояние кнопки. |

Правило следует ограничить булевыми полями и свойствами состояния/настроек.
Оно не должно требовать переименования `TryGet`, `TryFind`, `Equals`,
операторов сравнения или `Execute(..., out resultState)`: их bool означает
результат операции. `Was` — полезное уже существующее соглашение, а не ошибка
логики. Вопрос `HUD`/`Hud` нужно решить до переименования свойства.

Результат: по имени понятно, является значение состоянием, настройкой,
историческим признаком или результатом попытки операции.

### 1.3. Правило Validation/Errors выполнено не полностью

Это сопутствующее расхождение с уже принятым соглашением о ролях, а не
предложение новой архитектуры.

- `CommandLineService.ValidateKey` — собственный static-метод в сервисе,
  хотя `Validate*` должны находиться в `*Validation`.
- `DebugToolsEditorWindow.ValidateConfiguration` содержит саму проверку
  состава ProjectContext и строки диагностики.
- `EnemySpawnComponent.ValidateConfiguration` делегирует статическому
  валидатору. Проверки уже выделены, но название оболочки буквально попадает
  под запрет размещать `Validate*` вне `*Validation`.
- `EnemySpawnValidation` и `EnemyAbilityValidation` формируют строки ошибок
  непосредственно; соответствующих `EnemySpawnErrors` и `EnemyAbilityErrors`
  нет.

Предложение: перенести реальные правила и диагностические сообщения в
соответствующие `Validation`/`Errors`. Для делегирующих оболочек выбрать
один вариант: разрешить их явно или вызывать static-валидатор снаружи,
как это уже сделано для Player. `OnValidate` — callback Unity; его имя
нельзя менять, и само наличие callback не является нарушением.

Результат: существующее разделение ролей перестаёт зависеть от конкретной
фичи. Не следует выделять каждый локальный null guard в отдельный класс:
это соглашение о переиспользуемых правилах проверки, а не запрет guard clauses.

## 2. Неоднозначные правила и смысловые расхождения

### 2.1. Base: общее правило, специализированные базы и generic-определения

Общая секция Naming говорит «Base when useful», секция Abstract требует
`Base`, а валидатор проверяет этот префикс только в Abstract. Из-за этого
чистый Strict не отвечает на вопрос, должны ли все абстрактные классы иметь
этот префикс.

Адресные кандидаты:

- `EnemyBehaviourState` — абстрактная MonoBehaviour-база конкретных
  `EnemyBehaviour*State`. `BaseEnemyBehaviourState` понятнее и соответствует
  соседним `BaseMovementState`/`BaseNetworkStateMachine`.
- `MemberHandler` и `PayloadMemberHandler<TPayload>` — абстрактные
  MonoBehaviour-базы. Возможные имена: `BaseMemberHandler` и
  `BasePayloadMemberHandler<TPayload>`.
- `HandlerPayload` в Shared — также абстрактная база; имя нужно оценить
  вместе с правилами Shared, а не механически применить feature taxonomy.
- `ScreenDefinition<TScreen,TSettings>`,
  `SceneDefinition<TScene,TSettings>`,
  `PopupDefinition<TPopup,TPayload,TResponse>`,
  `LoadingScreenDefinition<TScreen,TSettings>` — повторяющееся семейство
  абстрактных generic-определений поверх негeneric `Base*Definition`.

Предложение: применять `Base` к обычным абстрактным основам и отдельно
описать существующее семейство generic definitions. Оно уже консистентно
внутри себя; менять четыре публичных семейства только ради префикса
необязательно. Прежде чем расширять автоматическую проверку, нужно явно
определить это исключение и границы правил Shared.

Результат: понятно, какой тип является базой для наследования; полезный
generic API не переименовывается без отдельной выгоды.

### 2.2. Суффикс System имеет разные значения

Документация описывает System как исполнителя runtime-правил над сущностями
или состоянием. Сейчас:

- `MovementSystem` делегирует `FillEntityIds`, `TryFindEntityId`, сортировку
  и `ApplyToAll` в `IGameEntityComponentAccessor`.
- `DamageableSystem` и `DamageSourceSystem` предоставляют аналогичный API,
  специализированный на компонентах Combat.
- `ScreenNavigationSystem`, `PopupSystem`, `LoadingScreenSystem` управляют
  состоянием, историей и awaitable UI-операциями.

Первые три типа не реализуют правила движения/нанесения урона, как может
ожидаться из их имён. UI-системы используют System в более широком смысле
подсистемы со своим состоянием. Это не доказательство runtime-ошибки.

Предложение: сохранить полезное существующее значение UI System и описать
его, но отдельно рассмотреть имена фасадов поиска сущностей. Например,
`DamageableEntityService`/`DamageSourceEntityService` или роль Repository,
если API будет ограничен запросами коллекции. `Accessor` подходит контракту
чтения, но не полному API с `ApplyToAll`. Для `MovementSystem` дополнительно
важно, что generic-параметр ограничен только `class`, а не movement-контрактом:
одного переименования недостаточно, чтобы доказать предметную специализацию.

Не следует массово заменять System на Service. Решение должно учитывать
фактический API и потребителей каждого типа.

Результат: имя не обещает симуляцию или combat-правила там, где предоставлен
доступ к коллекции компонентов.

### 2.3. Сокращения разрешены, но их канонический формат не выбран

`CONVENTIONS.md` допускает uppercase-сокращения и требует консистентности
связанных имён. В коде есть:

- `NetworkEntityIdData`, `EntityId`, `BufferedCommandId`;
- `TargetID`, `LogID`, `_selectedLogID` в инструментах диагностики;
- `DebugVisualizationHudWidgetView`, `DebugVisualizationHudValueData`,
  `HudVisible`, но `PrototypeGameHUDScreenView`;
- `LocalSaveDocumentDTO<TData>`, `JsonLocalSaveSerializer`, `NtpTimeProvider`.

Это не означает, что каждое употребление `Id` нарушает правило: документ
говорит «may preserve», а не требует uppercase во всех именах.

Предложение: добавить небольшую таблицу канонических форм. Практичный вариант
для данного проекта: `Id`, `UI`, `HUD`, `DTO`, `FPS`, `FOV`, `Json`, `Ntp`.
`ID`/`Hud` можно выбрать вместо этого, но нужен один осознанный выбор.
Имена внешних API (`GetInstanceID`, Photon/Unity contracts) сохраняются.

Результат: новые типы и члены не создают очередной вариант написания;
действующий `NetworkEntityIdData` не требует повторного массового rename.

### Предметный префикс и порядок слов

В активном коде последовательно используются `Player*`, `Enemy*`,
`NetworkEntity*`, `DebugConsole*`, `DebugVisualization*`. Но общего правила
порядка слов нет: существуют `PlayerLocomotionState`,
`LocomotionMovementConfig`, `EnemyChaseConfig`; в legacy есть
`LocomotionPlayerMovementState`.

Предложение для новых типов: `[I|Base]<Subject><Detail><Role>`, например
`EnemyDashAbilityComponent`, `PlayerFourDirectionalFacingProcessor`,
`MovementLocomotionConfig`. Префикс нужен, когда защищает от неоднозначности
в плоском namespace; это не требование механически повторять название
папки Feature во всех классах. `JsonLocalSaveSerializer` и
`ZenjectNetworkObjectProvider` могут сохранять привычный префикс механизма.

Legacy `Prototype` не следует переименовывать целиком ради одинакового порядка
слов. Совпадения имён между Prototype и TechnicalPrototype находятся в разных
namespace; generic/non-generic пары также не являются коллизиями.

### Enum и поведенческий State

В проекте есть singular `NetworkEntityType`, `PlayerMovementState`, а также
plural `LocalSaveStorageTypes`, `PopupStates`, `DebugToolTypes`. Текущий документ
разрешает обе формы — это не нарушение.

Для новых enum можно предпочитать singular, когда одно значение обозначает
один вариант; plural оставлять для flags. `StateType` стоит использовать,
когда это помогает различить идентификатор состояния и класс `*State`, как
в `EnemyBehaviourStateType`. Массовая миграция существующих enum ради формы
числа имеет низкую полезность.

## 4. Что не требует исправления

- `*T.cs` для generic типов уже документировано; найдено 14 таких файлов.
  `LocalSaveDocumentDTOT.cs` соответствует правилу, хотя выглядит непривычно.
- `Data`, `Model`, `DTO`, `Payload` следует выбирать по назначению.
  `InputBufferStateModel` и `EnemyDashStateModel` остаются runtime state,
  хотя реализуют `INetworkStruct`; наличие сетевой сериализации само по себе
  не требует суффикса DTO.
- `NetworkEntityIdData` соответствует текущей категории Data и представляет
  типизированное значение. Наличие equality и проверки конструкции не делает
  его Service и не требует нового суффикса ValueObject.
- Shared имеет свой словарь примитивов (`Result`, `Error`, `BoundedBuffer`,
  `IComposite`). Feature folder/suffix taxonomy не нужно переносить туда.
- Интерфейсу не требуется свой Feature или своя новая папка по суффиксу.
- Для каждого будущего паттерна не нужно заранее расширять словарь ролей.

Автоматизировать стоит только объективные правила после уточнения их границ:
имя файла, разрешённые суффиксы, prefix абстрактных баз с исключениями,
канонические сокращения в собственных объявлениях. Определение роли
System/Service/Provider по поведению остаётся задачей code review.

При переименовании Unity-типов сохранять `.meta` и GUID, применять `MovedFrom`
для соответствующих сериализованных типов и `FormerlySerializedAs` для полей.
Проверять также публичные имена, которые могут участвовать в reflection,
managed references или форматах сохранения.
