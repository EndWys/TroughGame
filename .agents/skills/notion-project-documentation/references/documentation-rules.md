# Notion Documentation Rules

## Purpose and Sources

Re-fetch live standard/process pages from `docs/notion/project.json` and the map in
`docs/notion/documentation-standard.md`. The enabled project Notion documentation
skill already serves this project; use its page, not a competing template.
Formatting does not authorize product/scope changes or arbitrary remote writes.

## Content Rules

Each topic has one canonical owner. Original contracts preserve accepted expectations;
delivery sections record implementation. Preserve both and the decision basis when
they differ; never rewrite requirements to manufacture a passed status.
Applicable sections: goal/behavior; scope/dependencies/entry points; accepted decisions
with reason/source; limits/deferred work; requirement/acceptance-criteria (RQ/AC) results,
checks, peer roles, Play Mode; actual supplied commit/PR references; native links to
tasks/features/documents. Omit empty sections.
Label facts/hypotheses/proposals. Unaccepted discoveries belong in authorized
observations/drafts, not the accepted plan. Creation requires exact permitted
parent/type and no suitable canonical document.

## Presentation and Evidence

Use small precise updates, connected prose, comparison/traceability tables.
Follow the live project's language/presentation standard for Notion pages.
Do not publish credentials, detailed local logs, private machine/journal paths.
A local file is not colleague-accessible evidence; publish factual summaries and
supplied accessible artifacts. Do not upload files/expose repositories just to
manufacture evidence URLs.
Private journals retain receipt/hash/source versions/target IDs/applied content/
values/readback. They support retry/audit, not product policy or development state.
