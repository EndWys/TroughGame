# UI Stage Response Forms

## Purpose and Common Envelope

Use the developer's request language for rendered headings/tables/prose. These
English forms define required content, not response language. Lead with the current
result or concrete decision. Show applicable detail in chat; artifact links do not
replace the proposal. Omit empty/inapplicable tables and use verified names.

Every handoff ends with: **current phase/status; next action; actor; approval or
blocking dependency**. Distinguish fact, inference, proposal, passed, failed and
not tested. State precisely what work follows acceptance. When stopping, link the
exact rule and quote its relevant instruction briefly. Do not ask again for an
unchanged accepted plan.

## Analysis

| Region / Behavior | Source / Observed Fact | Inference / Open Decision | Existing Counterpart |
| --- | --- | --- | --- |
| Actual region/state | Mockup/code/runtime evidence | Reason and confidence | View/template/service/resource path |

Describe the intended behavior, design/source dimensions, relevant states and
actual host. Next action is hierarchy/resource/presentation planning or a specific blocking
clarification. For a bug use the bugfix evidence/hypothesis forms as well.

## Consolidated Architecture and Resources

Show an indented proposed hierarchy with meaningful element names, template reuse,
viewport/row/overlay boundaries and binding points before implementation.

| File / Type / Element | Reuse / Create / Change | Responsibility / Exact API | Owner / Lifetime |
| --- | --- | --- | --- |
| Concrete proposed name/path | Action | Observable role and changed signatures | Construction/release point |

| Element / Target Property | Presentation Property / Action / View Contract | Mode / Trigger / Synchronization | Validation / Effect |
| --- | --- | --- | --- |
| Actual UXML name/property | Exact ViewModel or Presenter/View member | ToTarget / TwoWay / input event / explicit View update | Domain authority, busy/error/cancel |

| Resource / Purpose / Owner | Searched Locations / Found Path | Fit / Import / Size / States | Proposed Decision |
| --- | --- | --- | --- |
| Sprite/font/icon and owning scope | Feature and root CommonUI locations actually inspected | Reuse evidence or mismatch | Reuse / supplied / missing / root promotion / generated placeholder |

Explain the selected pattern and actual execution chain, DI/factory ownership, hide/close policy,
panel/scaling/adaptive choices, dynamic collection strategy and planned checks.
Present meaningful options only. Identify one host approval covering the exact
revision and resource decisions; next action is approved visual prototype work.

Only when proposing MVP, add this comparison and the exact View interface and
Presenter signatures to the existing architecture inventory:

| Proposed Pattern | Compact MVVM Alternative | Concrete Benefit / Cost | State / Action Owner and Check |
| --- | --- | --- | --- |
| MVP for the actual unit | Specific properties/actions and synchronization | Reduced code/coordination or clearer interaction, with tradeoffs | Exact Presenter/View responsibilities and observable verification |

Acceptance of this choice is part of the same architecture gate. Do not require
this comparison for every ordinary MVVM window.

## Visual Prototype

Show source and actual render evidence where available, with resolution/panel/data
context. Name mock behavior and remaining functional work.

| Region / State | Target | Actual Result / Difference | Correction / Decision |
| --- | --- | --- | --- |
| Actual region | Approved design | Screenshot/evidence or not rendered | Exact adjustment or accepted deviation |

List used/generated resources and placeholders still requiring replacement.
Request acceptance of this visual revision only. Explain which bindings/commands/
lifecycle work follows; do not claim complete behavior or final diff acceptance.

## Iteration and Host Return

| Feedback / New Evidence | Accepted Revision Impact | Exact Correction | Retest / Gate |
| --- | --- | --- | --- |
| Concrete point | Within scope or material revision | Files/elements/members | Reused evidence or new required check |

On return state accepted UI outcome, current host FEAT/case/phase, decision/evidence
references, remaining placeholder or verification work, and the next host action.
The host owns checkpoint/commit; only immutable accepted facts go to Notion workers.
